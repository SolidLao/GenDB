# MQO Mode — Multiple Query Optimization (Fused Execution)

## Overview

MQO mode (`--optimization-mode mqo`) generates a **single fused C++ binary** that executes an entire batch of SQL queries in one coordinated pass over the data. Instead of scanning each table once per query (as in single-query mode), MQO scans each large fact table **once** and feeds each row to all consuming queries simultaneously — amortizing I/O, cache misses, and scan overhead across the batch.

The key mechanism is **fused scan loops with runtime bitmask routing**:

```cpp
// Fused lineitem scan — 60M rows scanned once, feeding 10+ queries
#pragma omp parallel for schedule(static)
for (size_t i = 0; i < n_lineitem; ++i) {
    if ((active & Q1_BIT) && l_shipdate[i] <= q1_thresh)
        q1_local[tid].add(l_returnflag[i], l_linestatus[i], ...);
    if ((active & Q6_BIT) && l_shipdate[i] >= q6_lo && sd < q6_hi ...)
        q6_local[tid] += l_extendedprice[i] * l_discount[i];
    // ... one branch per consuming query
}
```

A `uint32_t active` bitmask controls which queries execute:
- `./mqo --gendb-dir <dir> --output-dir <dir> --all` sets all bits (fully fused batch)
- `./mqo --gendb-dir <dir> --output-dir <dir> --query Q3 --query Q6` sets only those bits (unused stages and branches are skipped at near-zero cost via branch prediction)
- `./mqo --list` prints supported queries

## Pipeline

MQO reuses Phase 1 (Workload Analyzer + Storage Designer) from single-query mode. Only Phase 2 differs:

```
Phase 1 (shared with SQO):
  Workload Analyzer  ->  Storage/Index Designer  ->  Query Guides

Phase 2 (MQO-specific):
  2.1  MQO Analyzer              -> shared_component_blueprint.json
  2.2  Global Skeleton Planner   -> batch_skeleton.json (fused stage DAG)
  2.3  Batch Code Generator      -> mqo_main.cpp + Makefile + manifest.json
       Build + smoke test + ground-truth validation
  2.4  MQO Optimizer (epsilon)   -> iterative profile-directed optimization
```

Total LLM agent calls: 3 (analyzer + skeleton planner + batch code generator) + N optimizer iterations. No per-query agents — all query logic is generated by the single Batch Code Generator.

## Agents

### mqo-analyzer/ — Shared Work Identification

Analyzes the query batch to identify which scans, hash builds, and aggregations can be shared across queries. Produces `shared_component_blueprint.json` listing each shared component with its kind, canonical signature, consumer list, and cost estimate.

**Two adaptive paths based on batch size:**

- **Small batch** (batch size <= `mqo.analyzerThreshold`, default 30): A single LLM agent reads all query SQL + schema + workload analysis + storage design and reasons holistically. Uses SQLGlot-backed structural tools (`src/gendb/tools/mqo-tools.py`) for deterministic lookups (table access patterns, join edges, predicate overlap, aggregation signatures).

- **Large batch** (batch size > threshold): A multi-step flow that preserves global information without context overflow:
  1. **Global Surveyor** (single agent, tool-driven) — walks the batch via tool calls only, populates `global_registry.json` with all candidate shared components. This file is frozen after this step.
  2. **Deterministic clustering** (`mqo-clustering.mjs`, no LLM) — groups queries by shared-candidate overlap. Cross-cluster candidates are tagged.
  3. **Parallel Cluster Analyzers** (N agents) — each reads the global registry read-only and writes decisions to its own private `cluster_N/blueprint_shard.json`. No race conditions.
  4. **Deterministic merge** (`mqo-merge.mjs`, no LLM) — collapses shards by canonical signature, unions consumer sets, flags ambiguous cases.
  5. **Global Integrator** (single agent) — resolves ambiguous cases with LLM judgment, writes final blueprint.

Prompts: `small-batch.md`, `large-batch-surveyor.md`, `large-batch-cluster.md`, `large-batch-integrator.md`

### global-skeleton-planner/ — Fused Execution DAG

Designs the fused execution plan as a sequence of stages:

- **`parallel_build`** — hash table builds for dimension tables (customer, supplier, part, nation). Independent, parallelizable via `#pragma omp parallel sections`.
- **`fused_scan`** — single-pass scan of a fact table (lineitem, orders, partsupp). The stage specification lists `consumer_branches` — one per query that participates in this scan, with the per-row filter and action.
- **`finalize`** — per-query post-processing: sort, limit, CSV output. Sequential.

Also produces `query_stage_mask` mapping each query to its required stages and hash dependencies, used by the dispatcher for `--query Qi` runtime pruning.

Output: `batch_skeleton.json`

### batch-code-generator/ — Fused Code Generation

The most critical agent. Produces the **entire** fused C++ artifact in a single invocation:

**Inputs:**
- Shared-component blueprint (from MQO Analyzer)
- Fused execution skeleton (from Skeleton Planner)
- All 22 query guides (from Phase 1 Storage Designer Pass 2) — exact file paths, C++ column types, index binary layouts, date encoding, dictionary details
- All SQL queries, database schema, workload analysis, storage design
- Hardware configuration (CPU cores, L3 cache size, total memory)
- Benchmark context (per-system sum-of-query-times as performance reference target)

**Outputs:**
- `mqo_main.cpp` (+ optional `stages/*.hpp`) — complete fused execution with bitmask routing, hash builds, fused scan loops, per-query finalize, argument parsing, profile flush
- `manifest.json` — query bitmask assignments and stage dependencies
- `Makefile` — single-command build

**Key design rules enforced by the prompt:**
- All I/O code is self-contained (no dependency on external `utils/` headers except `mqo_profile.hpp`)
- Query guides are the authoritative reference for binary data formats
- Parallelism is within fused scan loops (thread-local accumulators), never across queries
- CSV output: comma-delimited, header row, quoted strings containing commas
- The agent compiles, runs, and validates against ground truth before finishing (up to 2 fix attempts)
- Performance-First Implementation Framework: critical path identification, per-row work minimization, data structure fitness (ported from SQO code-generator)
- Comprehensive profiling: `MQO_TIME_DISPATCHER("dispatcher_total")` mandatory wrapping all execution, `MQO_TIME_SHARED` for shared stages, `MQO_TIME_TAIL` for finalize functions
- Data structure selection rules: bitsets for membership, direct arrays for small-cardinality, avoid `std::unordered_map` in hot loops, `alignas(64)` for thread-local accumulators

### mqo-optimizer/ — Profile-Directed Optimization (Strategy epsilon)

Iteratively improves the fused code using runtime profiling feedback. Uses the same quantitative diagnostic framework as the SQO Query Optimizer, adapted for fused execution:

**Diagnostic Framework (Steps 1-4):**
1. **Step 1 — WHERE**: Read `profile.json`, identify dominant regions by share of `dispatcher_total`, check optimization history to avoid repeating failed approaches
2. **Step 2 — WHY**: Q1 (plan wrong?), Q2 (implementation/hardware mismatch — compute memory footprints vs cache hierarchy), Q3 (wasted work?)
3. **Step 3 — WHAT**: Category A (plan restructuring), B (algorithm change), C (work elimination), D (parallelism tuning)
4. **Step 4 — Apply**: Minimal targeted edit addressing the root cause

**Context provided per iteration (mirrors SQO optimizer):**
- `profile.json` with `dispatcher_total` wrapping all execution and per-stage timings
- Hardware configuration (CPU cores, L3 cache size, total memory) — enables quantitative cache hierarchy reasoning
- Benchmark comparison (GenDB SQO, DuckDB, Umbra, ClickHouse, MonetDB, PostgreSQL — sum of per-query times as batch-total reference with "Target: beat X" directive)
- Full optimization history with timing, edit scope, edit summary, acceptance/rejection status — prevents repeating failed approaches
- Shared-component blueprint and batch skeleton for understanding the execution plan

**Per-iteration loop:**
1. **Measure** — run `./mqo --all`, collect `profile.json` (per-stage, per-region timings via `mqo_profile.hpp` instrumentation)
2. **Diagnose** — LLM follows Steps 1-4 diagnostic framework with quantitative analysis
3. **Decide scope** — one of: `fused_scan:<stage>`, `hash_build:<table>`, `query_branch:<qid>`, `finalize:<qid>`, `dispatcher`
4. **Edit** — LLM applies targeted patch to the identified bottleneck
5. **Rebuild + re-validate** — compile, run, check correctness against ground truth
6. **Accept or rollback** — accept if batch total improves by >= `minImprovement` without correctness regression; otherwise restore from snapshot

Stops when `maxIterations` reached or `stallThreshold` consecutive non-improving iterations.

## Design Decisions

**Why fused execution, not separate per-query binaries with shared intermediates?**
Materializing shared scan results to disk and having per-query binaries read them adds I/O overhead and loses pipeline fusion. Fused execution keeps data in CPU registers/cache across query branches within the same scan loop — the data is touched once and never written to memory between queries.

**Why runtime bitmask routing instead of compile-time specialization?**
A single binary that handles both `--all` and `--query Qi` via runtime bitmask avoids recompilation when switching modes. Branch prediction handles inactive branches at near-zero cost (< 1 cycle per row per inactive query after warmup).

**Why one Batch Code Generator agent instead of per-query agents?**
The fused execution model requires cross-query coordination (shared scan loops, shared hash tables, thread-local accumulator layout). A single agent sees the full picture and can reason about the fused loop body holistically. This also eliminates 44 per-query LLM calls (22 planners + 22 code generators), reducing wall-clock time by ~20 minutes.

**Why query guides from Phase 1?**
The Storage Designer's query guides document the exact binary format of every column file, index, and encoding for the specific data instance. Passing these to the Batch Code Generator eliminates format guessing and prevents the systematic I/O bugs (wrong zone map format, wrong column type, wrong delimiter) that plagued earlier versions without guides.

## Current Status — TPC-H SF10 (2026-04-10)

- **Correctness**: 22/22 queries validate against ground truth
- **Batch total**: **1236 ms** (dispatcher_total, hot run) — down from 3045 ms baseline after 5 optimizer iterations
- **vs SQO sum**: GenDB SQO sum-of-per-query = 1051 ms. MQO is 1.18x of SQO sum — near parity, with room for further optimization.
- **vs other systems**: MQO (1236 ms) beats DuckDB (2496 ms), ClickHouse (7313 ms), MonetDB (6508 ms), PostgreSQL (123503 ms). Comparable to Umbra (2072 ms).

The optimizer correctly used the diagnostic framework: all accepted iterations identified cache-exceeding data structures (Step 2 Q2) and replaced them with cache-friendly alternatives (Category B). Rejected iterations either had insufficient improvement (iter 2: 1.4% < 2% threshold) or introduced regressions (iter 3: over-threading).

### Generation costs

- **Batch Code Generator**: single agent call producing ~3000-5000 lines of C++ (30-60 minutes, $5-10)
- **Optimizer**: 5 iterations × ~5-10 min each
- **Total MQO Phase 2**: ~60-90 minutes, ~$15-25

### Known limitations

- **Incremental extension** (adding new queries to an existing MQO artifact without regeneration) is designed for but not yet implemented (v2).
- **Further optimization potential**: `load_data` (289ms) and `fused_scan_lineitem` (357ms) dominate. The lineitem scan could benefit from zone map pre-filtering, SIMD gather for filter evaluation, and further branch reordering by selectivity. Load time could be reduced with `madvise(MADV_SEQUENTIAL)` and selective loading.
