## The Fused Execution Model

Instead of running each query independently (22 separate scans of lineitem), scan each large
table ONCE with all consuming queries' operators interleaved in the same loop:

```cpp
// FUSED lineitem scan — all consumer queries in one loop
#pragma omp parallel for schedule(static)
for (size_t i = 0; i < n_lineitem; ++i) {
    int32_t sd = l_shipdate[i];
    if ((active & Q1_BIT) && sd <= q1_threshold)
        q1_local[tid].add(l_returnflag[i], l_linestatus[i], l_quantity[i], ...);
    if ((active & Q6_BIT) && sd >= q6_lo && sd < q6_hi && l_discount[i] >= 0.05 ...)
        q6_local[tid] += l_extendedprice[i] * l_discount[i];
    // ... one branch per consuming query
}
```

## Runtime Query Selection (bitmask)

uint32_t active = 0;  // bit i = query i is active

**`--gendb-dir`** is the path to the workload directory (e.g., `output/tpc-h-sf10`). Inside
it, binary data is at `storage/<table>/<column>.bin` and indexes are at `storage/<table>/idx_*.bin` or `storage/indexes/*`.
**`--output-dir`** is where per-query CSVs are written. **Create it if it does not exist** (`mkdir -p`).

## Parallelism Rules (CRITICAL — segfaults if wrong)

**NEVER run queries in parallel via `#pragma omp parallel for` over queries.**

Instead:
- Hash builds of independent dimension tables → `#pragma omp parallel sections`
- Fused scans → `#pragma omp parallel for` over ROW CHUNKS with thread-local accumulators, merge after loop
- Finalization → sequential (each query outputs independently)

```cpp
void fused_scan_lineitem(Context& ctx, uint32_t active) {
    const int nthreads = omp_get_max_threads();
    std::vector<Q1_Accum> q1_local(nthreads);
    // ...
    #pragma omp parallel
    {
        const int tid = omp_get_thread_num();
        #pragma omp for schedule(static)
        for (size_t i = 0; i < n_rows; ++i) {
            if ((active & Q1_BIT) && ...) q1_local[tid].add(...);
            // ... all consumer branches
        }
    }
    // Merge thread-local results
    if (active & Q1_BIT) for (auto& a : q1_local) q1_state.merge(a);
}
```

## Data Access: Use the Query Guides

Each query has a **query guide** (generated by the Storage Designer) that documents:
- Exact file paths for every column (`storage/<table>/<column>.bin`)
- C++ types for each column (`int32_t`, `double`, `int8_t`, etc.)
- Row counts per table
- Index files, their binary layout (zone maps, range indexes, hash indexes)
- Date encoding (epoch days since 1970-01-01, use `days_from_civil(y,m,d)` helper inline)
- Dictionary encoding details (dict files, code mapping)
- Cardinality estimates and selectivities

**Read all query guides first.** They are the authoritative reference for file paths and binary formats. Do NOT guess formats from storage_design.json when a guide exists.

### Data access patterns (from the guides):

**Binary columns:** mmap via `open()` + `mmap()`, cast to typed pointer, index by row.
```cpp
template<typename T>
const T* mmap_col(const std::string& path, size_t n) {
    int fd = open(path.c_str(), O_RDONLY);
    const T* p = (const T*)mmap(nullptr, n*sizeof(T), PROT_READ, MAP_PRIVATE, fd, 0);
    close(fd);
    return p;
}
```

**Row counts:** read from `storage/<table>/row_count.txt` (plain text integer).

**Date conversion:** dates are stored as `int32_t` epoch days (days since 1970-01-01).
```cpp
inline int32_t days_from_civil(int y, int m, int d) {
    y -= m <= 2; int era = (y >= 0 ? y : y-399) / 400;
    unsigned yoe = y - era*400, doy = (153*(m>2?m-3:m+9)+2)/5+d-1;
    unsigned doe = yoe*365 + yoe/4 - yoe/100 + doy;
    return era*146097 + (int)doe - 719468;
}
```

**Zone maps (if guide mentions them):** format documented in each guide's Indexes section. Read the meta file for block count, then read the binary array of `(int32_t min, int32_t max)` pairs.

**Dictionary-encoded columns:** `.bin` file has encoded integer codes; `.dict` file has the string dictionary. Guide documents the exact mapping.

**String columns with offsets:** `.dat` has concatenated chars, `.off` has `uint32_t` offsets. `string[i]` spans `[off[i], off[i+1])`.

## Performance-First Implementation Framework

In fused execution, performance is determined by what happens in the **fused scan inner loops**
— the code that processes every row of the largest tables. Every unnecessary operation per row
is multiplied by 60 million (lineitem at SF10). Reason systematically about where time is spent.

### Critical Path Identification
The fused lineitem scan is almost always the dominant cost. All implementation effort should
prioritize making this loop as fast as possible. Hash builds, finalization, and output are
secondary unless the critical path is already optimal.

### Per-Row Work Minimization
In each fused scan, enumerate EVERY operation performed per row across all query branches:
memory loads, comparisons, hash lookups, branch evaluations, accumulations. For each:
- **Is it necessary here?** Can it be precomputed once before the loop (e.g., resolving
  a date literal to epoch days at compile time using `constexpr`)?
- **Is it in its cheapest form?** Use the most compact representation. Smaller data →
  fewer cache misses.
- **Can it be eliminated?** A pre-built bitset eliminates a runtime lookup; a direct array
  indexed by key eliminates hash probing.

### Data Structure Fitness
For each data structure in the fused scan:
- **Access pattern**: Sequential scan → maximize spatial locality. Random probe → minimize
  working set size.
- **Memory footprint**: Compute capacity × element_size × replication (nthreads for
  thread-local). Compare to cache hierarchy (L1 32KB, L2 256KB, LLC shared).
  If it exceeds LLC, random accesses will be cache-miss dominated.
- **Key design**: Use the most compact key the storage format allows. Smaller keys →
  more entries per cache line → fewer misses per operation.

### Data Structure Selection Rules
- **Dimension membership tests** (e.g., "is customer in BUILDING segment?"): use a **bitset**
  when max key < 10M. Bitsets are ~1000x faster than hash set lookups for membership tests.
- **Small-cardinality aggregation** (nation_id < 25, returnflag × linestatus < 6): use
  **direct arrays** indexed by the key. Zero hash overhead.
- **Medium-cardinality aggregation** (orderkey-based, 1.5M-6M keys): use **dense arrays**
  (`calloc`'d, sized to max key value) if memory permits, or compact hash maps if not.
  Never use `std::unordered_map` for >100K entries in hot loops — it is cache-hostile.
- **Thread-local accumulators**: align to 64 bytes (`alignas(64)`) to prevent false sharing.

## Instrumentation (CRITICAL for optimizer)

Include `mqo_profile.hpp` (already in the artifact directory via `-I.`):

```cpp
#include "mqo_profile.hpp"
```

**Every major phase MUST be instrumented.** The MQO Optimizer reads `profile.json` to decide
where to optimize. Missing timings = blind optimizer = wasted iterations.

**Required timers** (use the scoped timer macros — RAII, no manual END needed):

```cpp
int main(...) {
    // ... arg parsing ...
    
    { MQO_TIME_DISPATCHER("dispatcher_total");  // ← MANDATORY: wraps ALL execution
      
      { MQO_TIME_SHARED("load_dimensions"); load_dims(C); }
      { MQO_TIME_SHARED("fused_scan_lineitem"); fused_scan_lineitem(C); }
      { MQO_TIME_SHARED("fused_scan_orders"); fused_scan_orders(C); }
      // ... other stages ...
      
      { MQO_TIME_DISPATCHER("finalize_all");
        { MQO_TIME_TAIL("Q1_finalize"); finalize_q1(C); }
        { MQO_TIME_TAIL("Q3_finalize"); finalize_q3(C); }
        // ... all finalize functions ...
      }
    }  // dispatcher_total ends here
    
    MQO_PROFILE_FLUSH("profile.json");
}
```

**Macro usage rules:**
- `MQO_TIME_DISPATCHER("dispatcher_total")` — wraps the entire execution (MANDATORY)
- `MQO_TIME_SHARED("name")` — for shared stages (hash builds, fused scans, dimension loads)
- `MQO_TIME_TAIL("Qn_finalize")` — for per-query finalization (sort, output)
- `MQO_TIME_DISPATCHER("finalize_all")` — wraps all finalize calls
- `MQO_PROFILE_FLUSH("profile.json")` — at end of main() AFTER dispatcher_total scope ends

Include `<omp.h>` for OpenMP functions.
